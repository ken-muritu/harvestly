# Harvestly risk engine: Oracle PL/SQL port

Port of `../engine/harvestly_engine.py` (Python reference, v4, after reviews R1 and R2) to an Oracle package.

## Oracle target (stated plainly)

- **Designed to compile on both Oracle 19c and 23ai** (Autonomous Database Always Free, or a free oracleapex.com
  workspace). This is a design rule, not a test result. Since review R2 (C-02) the rule is: no BOOLEAN-returning
  function is ever called inside a SQL statement (BOOLEAN in SQL needs 23ai); reply statuses are VARCHAR2 values
  computed first (`hv_reply_status`); `hv_to_num` replaces `TO_NUMBER(... DEFAULT ... ON CONVERSION ERROR)` in PL/SQL;
  JSON paths are literals. The oldest features used are `TRUNCATE` in `JSON_VALUE` (12.2), `FETCH FIRST` and identity
  columns (12c).
- **23ai is the safer first target** if both are available. 19c support rests on that rule and on
  `tools/test_plsql_static.py`, a source check that fails if a BOOLEAN function reappears inside a SQL statement.
  It does not compile anything.
- Needs APEX (`APEX_WEB_SERVICE`) and ORDS; `EXECUTE` on `DBMS_CRYPTO` and `UTL_I18N`.

> **Honest status: nothing in this folder has ever been compiled or executed on an Oracle database.** No Oracle,
> Docker or SQL*Plus was available. Neither the package, `schema.sql`, nor `ords_handlers.sql` has met a real parser.
> What *was* checked is the logic, through a Python mirror of the package (see "Offline verification"), and a
> static source check for the specific defects review R2 found. Expect compile errors on first install: compile
> the package first, then `ords_handlers.sql` (look at `USER_ERRORS`), then `test_vectors.sql`, then `test_smoke.sql`.

## Install

Order matters: schema, package, ORDS, then tests.

**Autonomous Database Always Free** (SQL Developer Web, SQLcl or Database Actions > SQL):
1. Run `schema.sql` as a script (F5 in SQL Developer Web). It starts with `SET DEFINE OFF`.
2. Run `harvestly_engine.pks`, then `harvestly_engine.pkb` as scripts. Check the compile has no errors
   (`SELECT * FROM user_errors WHERE name = 'HARVESTLY_ENGINE';`).
3. Run `ords_handlers.sql` (needs ORDS enabled for the schema, and APEX installed, which ADB has).
4. Insert your wards and, optionally, the stockist / warehouse / co-op directory (`hv_wards`, `hv_places`), and secrets:
   ```sql
   INSERT INTO hv_wards (name, county, lat, lon) VALUES ('Kitale', 'Trans Nzoia', 1.0157, 35.0062);
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('sms_secret', '<long random string>');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('ussd_secret', '<another long random string>');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('at_ip_allowlist', '<comma list of Africa''s Talking callback IPs>');  -- MANDATORY, see below
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('at_username', 'sandbox');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('at_api_key', '<key>');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('at_base_url', 'https://api.sandbox.africastalking.com');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('telegram_bot_token', '<token>');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('telegram_secret', '<random string for the X-Telegram-Bot-Api-Secret-Token header>');
   INSERT INTO hv_config (cfg_key, cfg_value) VALUES ('hash_pepper', '<long random string; losing it orphans every stored hash>');
   COMMIT;
   ```
   `hv_config` holds secrets in clear text: do not grant it to anyone else. Better for production: APEX Web Credentials.
   The three secrets (`sms_secret`, `ussd_secret`, `telegram_secret`) must be at least 16 characters; a shorter one is refused (R3 C3-10).
   `hash_pepper` is mandatory: `address_hash` raises ORA-20004 without it. The schema does not seed it on purpose.
   The package needs `EXECUTE` on `DBMS_CRYPTO` and `UTL_I18N` (as ADMIN: `GRANT EXECUTE ON DBMS_CRYPTO TO <schema>`).
5. Telegram: `curl "https://api.telegram.org/bot<token>/setWebhook" -d url=https://<host>/ords/harvestly/hv/telegram -d secret_token=<telegram_secret>`.
   Africa's Talking dashboard: SMS callback `https://<host>/ords/harvestly/hv/sms/<sms_secret>`, USSD callback `https://<host>/ords/harvestly/hv/ussd/<ussd_secret>`.
   **Webhook authentication (R2 C-05):** Africa's Talking does not sign callbacks. The path secret is necessary but leaks into
   access logs, so the source-IP allowlist is also required and fails closed: with `at_ip_allowlist` missing or empty every SMS
   and USSD callback gets 403. Get the callback IPs from Africa's Talking (they are not in this repo; unverified). For the
   sandbox only, the value `DISABLED` switches the IP check off. Behind a proxy or load balancer set `trusted_proxies` to its
   IP, otherwise `X-Forwarded-For` is ignored. Telegram is authenticated by the secret header.
6. Create the schedules described at the bottom of `ords_handlers.sql`. All of them are required:
   weather refresh 16:45 EAT, daily run 17:00 EAT, **the sender every 5 minutes at :02/:07/... (never exactly 17:00;
   without it no message ever leaves)**, retention purge 02:30. 14:00 UTC is 17:00 EAT if the form is UTC.
   The daily run only queues messages; the sender only sends what `claim_queued` hands it.

**oracleapex.com free workspace** (test data only): SQL Workshop > SQL Scripts > upload each file and run it, in the
same order. Notes: SQL Workshop may reject `SET ...` lines (delete them); ORDS and outbound HTTP are restricted on
the free service, so skip `ords_handlers.sql` sections 4 and 6 and demo through the tests and `daily_run_batch`.

## Run the tests

```sql
@schema.sql
@harvestly_engine.pks
@harvestly_engine.pkb
@vectors_data.sql        -- (re)creates hv_vec_* test tables
@test_vectors.sql
```
(In SQL Developer Web or APEX, open each file and run it as a script in that order.) Output is one `PASS`/`FAIL` line per
step, e.g. `PASS demo_pitch d3 evening DRY_NOW LOW left=34 m=17.3 life=7.3%`, then `=== N passed, 0 failed ===`.
It raises ORA-20999 if anything failed. What it checks:

- 49 EMC and 60 AST values to 1e-6.
- Each scenario day by day, replies first, then the evening run. Compared per step: reply command, message code and the
  EXACT message text, then code, risk level, days left (exact), the displayed moisture and life-used strings, and the
  exact values.
- Every template, both languages, worst-case fill, is GSM-7 and at most 2 SMS segments, with no leftover `{}`.
- Rounding (golden ties and a loop over 5.00 .. 40.00 step 0.01), evidence strings, the opt-out words, the 1000-character
  cut, address canonical form and HMAC-SHA256 hash (needs `DBMS_CRYPTO`), and 113 days-left cases including the 365 cap.
- Rules with no vector file: HIGH_ALERT weekly and capped, the STATUS text never says "safe" and promises nothing, a
  4000-character reply is answered with HELP, a second daily run the same day sends nothing, stale weather is flagged.

To regenerate after the Python engine changes: `python3 tools/build_schema.py && python3 tools/gen_vectors_sql.py`.
`gen_vectors_sql.py` refuses to run if its copy of the three scenario weather rules no longer reproduces `vectors.json`.

## Offline verification (what was actually run)

`python3 tools/simulate_port.py` (about 30 s). It is a line-by-line Python mirror of the package's control flow:
38-digit `Decimal` for NUMBER (ln, exp, Oracle half-away `ROUND`), `None` for NULL (Python raises on an unguarded
NULL comparison, where Oracle would silently treat it as false), the same regex strings (read out of the `.pkb`),
the same character loops for `normalise` and `sanitise_place`, and the EMC/AST tables and templates parsed back out
of `schema.sql`. It passes:

1. all of `vectors.json`: 49 EMC, 60 AST, 114 scenario steps with the exact message text, display strings and exact
   values, and the rounding, evidence, opt-out, normalise, address-hash and days-left sections;
1b. the rounding fuzz: every x from 5.00 to 40.00 step 0.01 through `fmt0/1/2` in Python, the mirror and the JS port
   (run with node), against exact half-up integer arithmetic: 0 divergences;
2. 1,500 random `render()` calls against the Python reference, both languages, random weather metadata, HIGH_ALERT
   counts, with GSM-7 and 2-SMS checks;
3. `normalise` and `apply_reply` against the reference for a corpus of about 500 strings (typos, decimals with comma,
   Kiswahili, opt-out words, unicode spaces, 1,500-character input) over random batch states;
4. a differential fuzz of random batches, weather (including stale), missing days, second runs on the same day and reply
   sequences, mirror versus reference, comparing every message code, text, risk level, days left, advice, flags and batch
   state (60 scenarios by default; larger runs also pass).

This proves the *algorithm and the string handling as designed*. It does not prove that the PL/SQL compiles or that
Oracle's functions behave exactly as the mirror assumes. The database wrappers (locking, queueing, opt-out, retention) are
not mirrored; they are read-checked only.

## Known gaps

- **Never compiled or run on Oracle.** Most likely first-run problems: a PLS- compile error somewhere in the 1,200
  lines, the repeated `DEFAULT` clauses in the body headers (identical to the spec; delete them from the body if
  your version objects), and `REGEXP_SUBSTR` sub-expression numbering in `apply_reply` for the HYGRO pattern.
- Regex dialect: the reference uses `\b`, lookbehind and, since R2 C-14, `re.ASCII` / `[0-9]` so digits and word boundaries are
  ASCII-only exactly like the port's `[0-9]` and `[^A-Z0-9_]` (`SALT YES\u00c9` and Arabic-Indic digits now behave the same in
  both). The port uses POSIX classes with explicit end-or-non-alphanumeric checks and a loop for the "decimal point only
  between digits" rule. The mirror runs the same patterns under Python's `re`, which is not Oracle's regex engine.
- Rounding is decided once: `fmt(x, n)` = round half up on the decimal value after correcting binary noise to 10 decimals
  (Python `Decimal(f"{x:.10f}").quantize(ROUND_HALF_UP)`, PL/SQL `ROUND(ROUND(x, 10), n)`, JS string arithmetic on
  `toFixed(10)`). A meter reading of 13.25 shows `13.3` in all three, and the vectors compare exact display strings.
  Numbers with more than 15 decimals in a reply are cut at 15.
- NUMBER arithmetic is decimal and Python's is binary double: results can differ around 1e-15. A days-left threshold that
  lands that close would flip by one day; none of the vectors or 150 fuzz scenarios did.
- The package is session-stateful (tables and templates cached per session). After editing `hv_emc`, `hv_ast` or
  `hv_templates` call `harvestly_engine.reset_cache`. Recompiling the package still raises **ORA-04068** once in every
  pooled session that had it loaded; this cannot be removed from inside the package. Retry the failed call (or flush the
  pool) after a deploy. Weather rows are assumed ascending with unique dates (`load_weather` orders them).
- The database wrappers (`load_batch`, `save_batch`, `process_reply`, `daily_run_*`, `hv_*` procedures) are not covered by
  the golden vectors and have no test at all. In particular `hv_ussd_menu`, `hv_handle_inbound` registration, the JSON_TABLE
  weather parsing, the ORDS definitions (parameter binding of `from`, `:body_text`) and the APEX_WEB_SERVICE calls are
  unrun sketches. `APEX_WEB_SERVICE` needs an APEX session: it works from an APEX Automation, not from a bare
  DBMS_SCHEDULER job.
- The engine keeps `b.sent` and `b.replies` as lists loaded from `hv_messages` and `hv_inbound`; `b.acks` from the Python is
  not kept (the `cmd` column of `hv_inbound` records ACKs for the alert-to-action metric). `ward` is `ward_id`.
- Open-Meteo free tier is non-commercial and needs CC BY 4.0 credit; production needs a KMD/KAOP agreement or a paid plan.
  Africa's Talking sandbox SMS only reaches the simulator; a Telegram user must message the bot first.
- Message sending is one API call per message (texts differ per farmer), so the 1,000 calls/day APEX default limit
  allows roughly (1,000 minus the ward count) messages a day until it is raised.
- Dates use the Africa/Nairobi calendar day (`today_eat`), because `SYSDATE` on ADB is UTC. Tests pass explicit dates.

## After review R1: behaviour you must know

- **Consent is per phone.** An opt-out word (`STOP`, `STOPP`, `UNSUBSCRIBE`, `CANCEL`, `END`, `QUIT`, `ACHA`, `SITISHA`,
  `SIMAMISHA`, `NISITISHIE`, or the phrases `NO MORE`, `OPT OUT`, `SITAKI TENA`) **anywhere in a message of at most 6 words**
  (R1-04: "I WANT TO STOP" works; longer messages are never read as opt-outs) stops every batch of the number and cancels its
  queued messages. The only message after a STOP is the one-line confirmation, which is exempt from the opt-out check in both
  claim paths (R2 C-01) and is sent once (a repeated STOP is silent). A stranger's STOP is confirmed too. `START` / `ANZA` reverses it. Opt-outs are stored as hashes in `hv_optout`; the
  row survives `erase_by_phone` so an erased person who said STOP is never messaged again.
- **Locking and idempotency.** `load_batch` takes `SELECT ... FOR UPDATE` (waits up to 30 s), so a reply and the 17:00 run
  cannot overwrite each other. `daily_run` records `hv_batches.last_run`; a second run on the same day sends nothing
  and says `already run today`. A unique index allows one PROACTIVE message per batch per day.
- **Sender protocol.** `claim_queued` marks rows SENDING with `FOR UPDATE SKIP LOCKED` and commits before any HTTP call;
  `mark_sent` / `mark_failed` close them. A failed send is retried up to 3 times, then FAILED. A row stuck in SENDING
  for 15 minutes (crashed sender) returns to QUEUED, so delivery is at-least-once in that rare case.
- **Only delivered messages count.** A SKIPPED (not GSM-7, or more than 2 SMS), CANCELLED or finally FAILED message is
  taken back out of the cap counters, and what it changed on the batch is restored (`undo_*` columns).
- **HIGH alerts are capped, then a closing state (R2 C-12).** A HIGH batch whose normal messages are capped gets a HIGH_ALERT
  at most weekly, at most 4 per test result. The 4th says: "Our last reminder. Retest: reply
  e.g. METER 14.2 (your own reading) or SALT YES/NO to restart." After it the engine stays silent ON PURPOSE (the run log flag is `high alerts used up`)
  until the farmer sends a new test result, which starts a new count. This is a deliberate trade: no spam, but a batch at
  0 days left can go quiet for weeks unless the farmer replies. The site and deck must say so. The countdown of 365 days is
  a cap ("365 or more"), never a prediction.
- **Weather freshness.** `record_weather_fetch` (autonomous transaction) records every success and failure. Advice built
  on weather older than 24 hours is flagged `weather stale` in `hv_run_log`, never triggers a rain alert, and the message
  shows the date of the data, not today's. With no fetch record at all the weather counts as stale.
- **Messages.** The STATUS text says what was measured and when, labels the time left an estimate, and never says
  "safe" or promises a future message. Every alert carries `Open-Meteo.com` and the data date; the WELCOME message
  carries the full attribution. Replies longer than 1,000 characters are cut before parsing and never raise.
- **Privacy** (details and retention windows below).

## Privacy and retention

| Data | Kept | Then |
|---|---|---|
| Phone number / chat id of a batch (`hv_batches.farmer_ref`) | while the batch is active | blanked 90 days after it is closed or stopped |
| Recipient address of a message (`hv_messages.to_addr`) | until sent / failed / cancelled | blanked at once (retention backstop: 30 days) |
| Raw inbound text (`hv_inbound.raw_text`) | known senders only, 30 days | blanked, and the normalised text (250 chars max) is blanked at 30 days too (R2 C-09; unknown senders store no text at all) |
| Message rows | 180 days | deleted. While a batch is active its cap rows are kept (TEST_FIRST / INSECT_REMINDER, and every row dated on or after its last test, because the HIGH_ALERT and repeat caps count per test result), with the text replaced by `[purged]` (R2 C-10, R3 C3-03) |
| Rate-limit and replay rows (`hv_rate`, `hv_inbound_seen`) | 2 / 7 days | deleted |
| Run log | 90 days | deleted |
| Identity used for matching | `farmer_hash` / `from_hash` / `to_hash` = HMAC-SHA256 of the canonical number with `hash_pepper` | kept with the row |

`harvestly_engine.purge_retention` (scheduled daily) applies these windows. `harvestly_engine.erase_by_phone(channel,
number, deleted)` removes one person's batches, messages, inbound log and run log on request (pass NULL for the channel
to erase every channel). Messages from an unknown sender store only the hash and the command. Use the number only to
send; keep `hv_config` and the pepper out of backups that leave your control. The retention windows are programme
choices, not legal advice; check them against the Kenya Data Protection Act 2019 and register with the ODPC if required.

## After review R2: what changed in the Oracle layer

In short: no BOOLEAN in SQL (C-02); `:body_text` read once into a local
CLOB and form fields parsed from it, no reliance on ORDS parameter binding (C-03, R1-12); STOP confirmation delivered (C-01);
Telegram token mitigation and honest comment (C-04); replay protection on the Africa's Talking `id` and Telegram `update_id`,
per-phone hourly inbound and reply caps, a system-wide how-to cap, a per-phone registration cap, IP allowlist on by default,
XFF trusted only from listed proxies (C-05, C-13); START works for an opted-out stranger (C-06); USSD status reuses the SMS
wording helpers (C-07); `sent_at` set on every claim, TIMESTAMP WITH TIME ZONE columns (C-08); no text kept for unknown senders
(C-09); cap rows survive retention while the batch is active (C-10); byte-safe USSD parts and truncating JSON reads (C-15);
Telegram addresses are `tg:<id>` (C-16); welcome queued before the test message and the 2-segment rule applied (C-17).
`reset_cache` clears only the calling session (R1-21): after changing templates or tables, call it in every pooled session or
restart the ORDS pool.

## After review R3: what changed in the Oracle layer

In short:
- **One STOP confirmation, ever (C3-01).** `process_reply` looks at `hv_optout` before it applies the STOP, so only the
  transition into opt-out is confirmed; a repeated STOP from a known sender is processed and silent, as for a stranger.
- **Budgets (C3-02).** The reply budget moved into `harvestly_engine.reply_status` and `queue_message` applies it to every REPLY
  row (known senders and the welcome too). New limits: `max_reply_global_per_day` (3000), `max_batches_global_per_day` (300),
  `max_ussd_per_hour` (30, USSD now has an inbound cap). The inbound counter is a sliding window (this hour plus the part of
  the previous hour not yet slid out), so the clock-hour boundary no longer allows twice the limit.
- **Caps survive retention (C3-03).** Purge keeps the cap rows of an active batch past 180 days and blanks their text.
- **Handlers.** USSD has an outer exception block and always answers a screen (C3-04). `from` / `phoneNumber` must look like
  a phone number (`^\+?[0-9]{6,15}$`), values are cut to the variable width, so a forged long sender is dropped with a 200
  instead of ORA-12899 / ORA-06502 and an AT retry loop (C3-05). Only a number is sent on as `METER` from the USSD prompt
  (C3-06). The daily registration cap is checked after the retry checks (C3-07). The inline send is OFF unless `inline_send` = `Y`
  (C3-08). Secrets under 16 characters are refused and compared in full without an early exit (C3-10). CORS is closed
  explicitly (C3-12). The START confirmation is the template `START_OK`, English or Kiswahili (C3-14).
- **Body parsing (R1-12).** `hv_body_ok` returns 0 for a malformed body and the handlers answer 400; `hv_body_value` reads form or
  JSON, from the CLOB.
- **Wording (E3-01, S3-01).** The closing HIGH alert names only commands the parser accepts ("e.g. METER 14.2 (your own reading) or SALT YES/NO"; R4 E4-01: example numbers are above the 13.5 limit, so copying one never records a dry reading);
  "falling fast in damp weather" is never shown for a sealed bag or a countdown at the 365 cap (`risk_text(..., p_tracks_air)`).

### Testing against a real callback (R1-12, C3-13): the one-callback procedure

Do this once on the sandbox before anything is claimed about SMS or USSD. Needs the Africa's Talking sandbox, a public HTTPS URL
for ORDS, and `at_ip_allowlist` = `DISABLED` for step 1 only.
1. Insert the config rows (`sms_secret`, `ussd_secret` of at least 16 characters, `at_ip_allowlist` = `DISABLED`, `ip_diag` = `Y`,
   `hash_pepper`, `at_username` = `sandbox`, `at_api_key`, `at_base_url` = `https://api.sandbox.africastalking.com`). Register one ward.
2. In the AT sandbox set the SMS callback to `https://<host>/ords/harvestly/hv/sms/<sms_secret>`, then use the simulator to send
   `JOIN KITALE SACK 5` from `+254700000001`. Expected: HTTP 200 in the AT callback log; a row in `hv_batches`; two QUEUED rows
   in `hv_messages` (WELCOME, TEST_FIRST). If the log shows 400, the body was not a form or JSON body: copy the raw body
   from the ORDS access log into `hv_body_ok` / `hv_body_value` in SQL Developer and fix the parser.
3. Run `SELECT provider_id FROM hv_inbound_seen WHERE channel = 'ipdiag';` and note `REMOTE_ADDR` and `XFF`. Put the AT
   addresses (exact IPs, no ranges) into `at_ip_allowlist` (add the proxy to `trusted_proxies` if `REMOTE_ADDR` is a proxy), set `ip_diag` = `N`,
   and send the message again: still 200. Send it from `curl` on another machine: 403.
4. Set the USSD callback the same way and dial the sandbox code: `1` (register), a ward, a storage, `5`; then `3`, `3`, `13.5`.
   Expected: screens of 160 characters or fewer, and `hv_batches` / `hv_batches.moisture` updated.
5. Run `test_smoke.sql`; then run `BEGIN hv_send_queued; END;` from an APEX Automation or `APEX_SESSION` and check the AT dashboard shows the SMS.
6. Only if you want replies sent from inside the handler: set `inline_send` = `Y`, repeat step 2, and check the reply arrives within
   seconds and `hv_messages.attempts` is 0. If it fails, leave it `N`; the sender job covers it.
Record the result (date, what was seen) before any claim is made.

### Upgrading an existing install (C3-11)

`schema.sql` only creates what is missing. It now stops with ORA-20099 if a table still has the pre-C-08 `TIMESTAMP` columns
(`hv_messages.created_at`, `sent_at`, `hv_weather_rain24.fetched_at`, `hv_weather_fetch.last_attempt_at`, `last_ok_at`). Changing
that type needs a column copy; for each column `c` of table `t`:
```sql
ALTER TABLE t ADD (c_new TIMESTAMP WITH TIME ZONE);
UPDATE t SET c_new = FROM_TZ(c, 'Africa/Nairobi');     -- or the zone the old values were written in
ALTER TABLE t DROP COLUMN c;
ALTER TABLE t RENAME COLUMN c_new TO c;
```
(Restore the `NOT NULL` and `DEFAULT SYSTIMESTAMP` where `schema_ddl.sql` has them.) Never run on production without a backup;
unrun like everything here.

  parse form-encoded fields (JSON accepted too). Africa's Talking's own docs could not be fetched (HTTP 403); the form-encoded
  format and field names come from third-party documentation. Run one real Africa's Talking **sandbox** callback against SMS
  and USSD before anything is claimed (R1-12).
- Whether APEX records `make_rest_request` URLs (the Telegram token) in its own log, and whether `apex_debug.disable` is
